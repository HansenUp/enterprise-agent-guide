# 4 指令工程

## C013 System / Developer / User Instructions（系统／开发者／用户指令） 【基础】

不同角色表达平台规则、应用规则和用户目标，具体优先级由模型供应商定义。企业业务授权必须由服务端校验，不能仅靠高优先级提示词。网页、知识库、录音转写中的“请忽略规则”属于数据，不能升级成平台指令。

## C014 Prompt Template / Prompt Versioning（提示词模板／版本管理） 【基础】

Prompt 定义任务、输入边界、输出契约和异常处理。建议将其作为配置资产纳入代码审查、版本发布、回滚和评测，而不是让每个销售或开发人员各自维护一份万能提示词。模板中留出受控变量，防止把用户内容直接拼入系统规则区。

## C015 Zero-shot / Few-shot Prompting（零样本／少样本提示） 【基础】

Zero shot 不提供示例；Few shot 用少量输入输出示例表达标准。菜单打标可提供易混品牌、同名菜及未知类别示例。示例要覆盖边界而非重复常见样本，并与正式标签表同步。示例数量不是越多越好，应以独立测试集效果判断。[S11]

## C016 CoT（Chain of Thought，思维链）/ Explainable Results（可解释结果） 【条件】

Chain of Thought 指通过中间推理组织求解的方法。显式要求“逐步思考”在部分早期模型有效，但推理模型未必需要，官方亦可能建议避免此类提示。不能将模型生成的思路当作真实因果或审计记录。保留事实依据、工具结果和决策摘要更实用。[S11]

## C017 Structured Output / JSON Schema（结构化输出／JSON 结构规范） 【基础】

结构化输出约束字段、类型、枚举等，通常比“请输出 JSON”更可靠。JSON 语法正确、Schema 合法、业务值正确是三层不同标准。Schema 能限制 stage 为枚举，却不能证明客户真的处于该阶段；还需业务规则、来源核验及拒答处理。[S12]

## C018 Prompt Optimization / Prompt Injection（提示词优化／提示注入） 【增强】

手工或自动优化 Prompt，应先定义指标、训练样例和保留测试集。避免针对同一批测试题反复调参而报告虚高收益。Prompt injection 是不可信数据诱导越权，不是简单的“提示词写得不好”；它需要执行边界与权限控制，不能用更长 Prompt 根治。[S13][S14]

实践要求：每份项目级 Prompt 至少说明输入来源、允许工具、事实与推断的表达方式、缺失信息处理、输出字段和禁止的动作，并配对应失败样例。
