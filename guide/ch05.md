# 5 Context Engineering（上下文工程）

## C019 Context Engineering（上下文工程） 【增强】

上下文工程决定每轮模型实际看到什么，包括规则、工具、任务状态、证据、历史和记忆。Prompt 工程是其中一部分，并未被替代。CRM 场景应按客户、时间范围与访问权限组装材料，优先放任务所需证据，而非一次塞入所有销售记录。[S02]

## C020 Context Budget / Information Density（上下文预算／信息密度） 【基础】

为不同上下文组成分配容量，并为模型输出预留空间。预算策略应依据任务测试调整，不宜用固定比例套所有场景。检索结果可返回摘要加定位符；大型报表先计算聚合再送模型。压缩 Token 的同时不能丢失否定词、时间、单位和来源。

## C021 Just-in-Time Retrieval / Progressive Disclosure（即时检索／渐进披露） 【增强】

先给模型目录、工具摘要或证据引用，需要时再加载细节。适合代码仓库、大知识库与复杂客户档案。收益是降低上下文负担，代价是额外调用和搜索失败。高频必需数据可预取，未知部分再探索；权限检查必须随每次读取执行。[S02]

## C022 Compaction / Summary Distortion（上下文压缩／摘要失真） 【增强】

Compaction 用摘要或结构化状态替换部分历史，帮助长任务继续。应保留目标、已验证事实、未决问题、产物位置和不可逆动作记录，并允许回查原始事件。不要只保存模型自由总结：它可能把推断变事实，或忘记已执行过一次写操作。[S05]

## C023 Context Rot / Lost in the Middle（上下文退化／中间信息遗漏） 【条件】

这些术语描述长上下文下性能下降或信息位置影响，不代表每个模型在所有任务中有同样退化。通过打乱证据位置、加入干扰文本、延长历史来测试自己的任务。更大的窗口能缓解容量不足，却不能解决权限、数据过期和来源冲突。[S02]

## C024 Citation / Context Provenance（证据引用／上下文来源追踪） 【基础】

每个重要事实应关联原文片段、业务对象、时间戳与版本。摘要保留引用，推荐区分“客户说过”“CRM 已确认”“模型推断”。引用只是定位能力，仍需检查来源是否支持结论；指向正确文件但错误段落也不能算事实正确。

平台建议：设计 Context Builder 服务，在模型前统一执行身份过滤、来源选择、去重、长度控制和引用分配；记录所用材料版本，但不要默认把全部敏感原文写入普通日志。
