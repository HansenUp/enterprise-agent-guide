# 9 Tool Engineering（工具工程）

## C043 Function Calling / Tool Use（函数调用／工具使用） 【基础】

模型输出工具名及参数，运行时执行后把结果送回模型，随后继续或结束。Function Calling 是交互机制，不等于模型能直接获得数据库权限。服务端必须验证参数、身份、业务约束与结果。调用函数成功与完成用户任务是两个指标。[S21]

## C044 Tool Schema / Business Semantics（工具结构规范／业务语义） 【基础】

工具需定义输入输出、必填字段、单位、枚举、异常及副作用。相比含糊的 operate_customer，拆为查询档案、预览修改、提交修改更容易控制。Schema 验证解决格式问题；客户是否属于当前销售、价格是否仍有效，需要业务系统判断。

## C045 Tool Discovery / Tool Search（工具发现／工具搜索） 【增强】

大量工具不应全部塞进每轮 Prompt。先按权限和业务域筛选，再按任务检索少量候选；真正调用前仍需验证工具版本和授权。描述应说明适用与不适用场景。工具发现失败会变成任务失败，因此要有可控回退和调用覆盖测试。

## C046 Programmatic Tool Calling / Code Mode（程序化工具调用／代码模式） 【增强】

模型生成短程序组合查询、循环、过滤与聚合，执行环境只返回必要结果，可减少逐个工具往返及中间数据进入上下文。它把风险从“参数调用”扩展到“代码执行”，必须配沙箱、调用白名单和预算。不能直接把生产凭证交给生成的程序。[S22]

## C047 Tool Idempotency / Structured Errors（工具幂等／结构化错误） 【基础】

幂等保证同一业务意图重试不会重复产生副作用；结构化错误区分参数错误、权限不足、业务冲突、限流及结果未知。幂等键应来自稳定业务操作 ID，而不是每次重试生成。模型可以修正参数，但不能通过反复重试绕过业务限制。

## C048 API（Application Programming Interface，应用程序接口）/ RPA（Robotic Process Automation，机器人流程自动化）/ Computer Use（计算机操作） 【条件】

有稳定 API 时优先使用 API；没有接口时可考虑 RPA 或基于屏幕的操作。Computer Use 可适应界面变化，但会受窗口状态、截图理解和焦点影响。关键动作应在执行前确认目标、执行后核验结果，并避免只根据点击动作判断业务成功。

工具设计例：recommend_products 返回候选商品、库存时间、价格版本和推荐原因；create_order 单独存在，并要求已确认的购物清单与授权凭据。推荐工具不隐式下单。
