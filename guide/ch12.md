# 12 多 Agent 的边界与协作

## C061 Single-Agent / Multi-Agent（单智能体／多智能体） 【条件】

多 Agent 是多个执行角色或实例协作，不一定使用不同模型。合理动因包括上下文隔离、专业工具权限隔离和独立并行工作。多个角色共享同一偏差时不会自然提升正确率。先有单 Agent 基线，再用相同预算衡量多 Agent 的收益。

## C062 Orchestrator-Workers（编排器与执行者） 【条件】

协调者拆解任务、委派并汇总结果，工作者完成受限子任务。适合需求动态变化、可分工的研究或开发任务。给工作者明确输入、输出、完成条件及预算；汇总者应检查冲突和缺失，不能把每个子结论直接拼成最终答案。

## C063 Handoff / Agent-as-Tool（任务交接／智能体作为工具） 【基础】

Handoff 是把对话或任务控制权交给另一 Agent；Agent as Tool 则由父 Agent 调用子能力并收回结果。客服转专家可用交接，商品分析可用工具式调用。设计必须明确责任归属、继承哪些上下文，以及授权是否继续有效，不能默认把父级全部权限传下去。

## C064 Parallelism / MapReduce（并行／映射归约） 【基础】

将独立任务分发并行，再汇总结果。适合分析多个客户、分片打标或读取独立资料。限制并发避免击穿模型额度和业务系统。存在前置依赖的任务不能强行并行；共享文件或数据库写入还需锁、版本控制或合并策略。

## C065 Blackboard / Shared State（黑板模式／共享状态） 【条件】

Blackboard 以共享结构承载多 Agent 的发现、计划及产物。它比互相广播完整聊天记录更可控，但需要字段所有权、冲突检测和版本。建议子任务写独立产物，协调者合并；禁止多个 Agent 无约束覆盖同一个客户结论字段。

## C066 Debate / Voting / Independent Verification（辩论／投票／独立验证） 【条件】

辩论、投票和交叉审查可暴露部分错误，但多个模型同意不代表证据可靠。应追求独立数据来源、不同校验方法和明确判定规则。对标签分类可比较模型与人工抽检；对金额计算应使用程序核验，而不是让三个 Agent 表决数字。

架构建议：Coding Harness 中的多个角色可以保留为能力目录，不必每次全部启动。根据风险和任务类型按需加载，并测试角色数减少后的完成率与成本。
