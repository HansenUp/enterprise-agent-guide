# 14 分布式执行与一致性

## C073 Event Log / State Store（事件日志／状态存储） 【基础】

事件日志记录发生过什么，状态库提供当前任务的可查询视图。建议事件追加写，状态更新带版本号；模型上下文是从中选择的材料，不是唯一账本。事件记录应遵守敏感数据保留策略，不能以可追溯为由无限保存所有客户原文。

## C074 At-Least-Once / Exactly-Once（至少一次／恰好一次） 【基础】

跨服务通常可能重复投递或出现结果未知。Exactly Once 的承诺必须限定作用范围；模型调用、消息投递和外部订单不共享一个天然原子事务。落地重点是业务幂等、唯一约束、状态查询和对账，而非在架构图上写“只执行一次”。

## C075 Saga / Compensation（Saga 模式／补偿操作） 【基础】

Saga 把跨系统流程拆成局部事务，失败时按业务规则补偿。撤销预留库存可以补偿，已发给客户的信息不能真正撤回。Agent 可以解释异常，但补偿动作应有明确契约和权限，不能让模型临时发明一条“逆操作”。

## C076 Outbox / Inbox / Deduplication（发件箱模式／收件箱模式／去重） 【基础】

Outbox 将业务状态与待发送事件写入同一事务，后台可靠投递；Inbox 记录已处理事件以防重复。适合 CRM 任务创建、标签批量入库等链路。消息 ID 用于投递去重，业务操作 ID 用于语义幂等，两者不要混用。

## C077 Retry / Circuit Breaker / Bulkhead（重试／熔断器／舱壁隔离） 【基础】

重试应区分可恢复故障与永久错误，使用上限、退避和抖动。熔断防止持续冲击故障服务，舱壁隔离防止某租户或工具拖垮全部任务。参数非法不能靠原样重试解决；写请求超时必须先核查结果，不能直接换模型再执行。

## C078 Optimistic Locking / Approval Expiry（乐观锁／审批过期）/ TOCTOU（Time of Check to Time of Use，检查与使用之间的时间差） 【基础】

TOCTOU 指检查与使用之间状态发生变化。生成菜单时有货，审批后可能缺货；查看客户时有权限，写入时可能已转交。使用 version、更新时间或条件写入重新校验。审批凭据绑定动作摘要，参数变化后重新确认，避免批准 A 却执行 B。

可靠性例：create_followup 超时后先以 operation_id 查询是否已创建；查不到且服务仍不确定时标为 pending_reconciliation，而不是立即重发三次。
