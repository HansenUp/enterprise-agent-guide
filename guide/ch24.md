# 24 技术选型与协议边界

先选控制模式和运行需求，再选框架。已有 Java 团队可以保留交易与权限体系，把模型能力接入现有服务；是否增加 Python 由生态收益、人员能力和运维成本决定。

| 选项 | 适合评估的用途 | 需要补齐或验证 |
|---|---|---|
| Spring AI 或 LangChain4j | Java 应用接入模型 工具 RAG | 任务持久化 策略和发布治理 |
| LangGraph | 有状态编排 中断恢复 Agent 图 | 外部副作用幂等 租户隔离 |
| Microsoft Agent Framework | 采用微软生态的 Agent 与工作流 | 版本兼容 迁移成本 部署约束 |
| Google ADK | Google 生态或多语言 Agent 开发 | 目标运行环境和治理集成 |
| Dify | 快速验证知识问答和可视化流程 | 权限颗粒度 复杂状态 可迁移性 |
| Temporal 或现有 BPMN 平台 | 跨服务长事务 定时 重试 审批 | 模型与上下文管理需另行实现 |

表中是评估方向，不是产品排名或功能穷举。官方入口见 [S10][S29][S30][S36–S39]。不要把 Temporal 的持久化执行与模型推理能力混为一谈，也不要把框架 checkpoint 当成跨系统交易保证。

## 四类协议或封装的关系

Tool schema 定义一个函数怎么调用；MCP 定义能力如何暴露与交互；A2A 定义独立 Agent 如何交换任务和产物；Skill 封装任务知识与可复用流程。它们可共存，并不构成必须按顺序引入的技术栈。

## 六项选型验收

验证真实业务成功率、故障恢复、权限与数据隔离、每次成功成本、调试维护效率、迁移与退出能力。对候选框架用同一任务集和约束测试；演示顺利、星标数量及“支持多 Agent”不能替代验收。

## 存量系统的渐进接入建议

现有认证和网关 + 业务工具适配（使用存量系统语言） + 一种模型接入框架 + 数据库任务状态 + 现有消息队列 + 评测流水线。确实存在跨天恢复或复杂补偿时再引入持久化工作流；出现实测收益时再增加独立 Agent。
