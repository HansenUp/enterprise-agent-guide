# 29 架构评审与趋势判断清单

## 十个必须能回答的问题

1. 哪些步骤需要模型判断，哪些步骤可以确定性执行？最简单基线是什么？
2. 事实来自哪里，如何检查更新时间、证据位置和访问权限？
3. Agent 代表谁执行，允许读什么、写什么，怎样撤销授权？
4. 工具超时、重复消息和任务恢复后，如何避免重复副作用？
5. 上下文、业务状态和长期记忆分别存在哪里，怎样删除与隔离？
6. 成功如何定义，测试集是否独立，哪些错误绝不能接受？
7. 每次成功成本和尾部时延是多少，预算不足如何安全降级？
8. 发布哪些组合版本，如何灰度、追溯、回滚及停用？
9. 增加子 Agent、反思、图检索或微调后，有什么实测增益？
10. 模型或框架停止服务时，状态、知识、工具及评测能否迁移？

## 趋势判断的证据层级

官方公告决定“已弃用或到期”；规范及产品文档说明“当前支持”；论文证明“特定设置下可行”；跨任务企业实测才支持“适合本业务”。技术流行度和市场主流预测不等于这些证据。每季度复核依赖版本和迁移窗口。

## 应持续投入的能力

高置信判断：权限与工具契约、证据与数据治理、评测与可观测性、任务状态与可靠执行仍是企业基础。中等置信判断：上下文工程、技能复用、托管运行时及 Agent 与流程组合会进一步发展。具体产品份额、统一记忆协议和完全自主多 Agent 组织仍有较高不确定性。

## 需要减少依赖的做法

超长万能 Prompt、无约束自动循环、把向量库当全部记忆、仅靠模型自评、无证据的自报置信度、让 Agent 自改安全门槛，以及为了角色数量拆分任务，均不宜作为平台默认设计。这是工程适用性判断，不是宣布对应技术已经被官方弃用。

## 掌握标准

能定义概念只是第一步。达到架构师要求，需要解释替代方案、指出失败模式、设计验证方法并给出迁移路径；达到高级开发要求，需要能够实现、观测、故障演练并维护这些边界。
