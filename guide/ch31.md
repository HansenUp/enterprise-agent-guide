# 31 分层架构与端到端执行链路

## 八层架构与所有权

| 层 | 核心职责 | 推荐实现与边界 |
|---|---|---|
| 体验与接入 | 聊天、任务、审批、产物、管理员门户 | TypeScript + React；现有企业门户优先；HTTPS API 与可恢复事件流 |
| 控制面 | 租户、应用、版本、配额、策略、目录、发布 | FastAPI 或存量 Spring Boot/.NET；PostgreSQL 元数据；不在控制面运行长任务 |
| 执行面 | 状态机、Agent 循环、检查点、预算、取消 | LangGraph 或轻量类型化 Agent；长事务按需 Temporal；worker 读取不可变发布版本 |
| 能力面 | 模型、检索、OCR、ASR、排序、传统 ML | 统一契约和能力清单；模型网关与推理池；模型提供方差异由适配器处理 |
| 工具面 | 内部业务 API、MCP、外部系统、代码沙箱 | 独立工具执行器进行授权、校验、幂等、限流；第三方输入不具备授权能力 |
| 数据面 | 原文、结构化事实、索引、记忆、任务产物 | PostgreSQL + 对象存储起步；检索按需独立；事实归业务系统 |
| 质量与运维 | 评测、追踪、成本、告警、事故、反馈 | OpenTelemetry；LLM 追踪与人工标注；现有监控体系；发布回归 |
| 安全与治理 | 身份、最小权限、隔离、数据生命周期 | 现有 IdP 或 Keycloak；策略服务；密钥管理；网络出口约束 |

推荐各服务通过 OpenAPI/JSON Schema 定义同步接口，异步结果包含任务 ID、事件序号、状态和产物引用。只有跨组织或独立运行的 Agent 协作才评估 A2A；内部普通函数无需额外协议层。

## 一次“查询并申请业务变更”的完整路径

1. 网关验证用户身份；服务端确定 tenant_id、用户与应用权限；限制输入尺寸并创建 run_id、trace_id、预算和截止时间。
2. 执行器读取固定 application_version，按数据分级选择允许的模型与工具；建立只包含授权数据的上下文。
3. 检索服务先做可访问范围过滤，再召回、排序、重排；返回 doc_id、版本、片段位置、证据与授权上下文。
4. Agent 形成结构化结果或工具提案。工具执行器重新验证业务条件，不能仅依赖提示词中的规则。
5. 写操作生成明确变更摘要与参数哈希；按风险取得审批，审批绑定用户、租户、工具版本、参数、有效期。
6. 执行时再次检查当前权限及业务状态；以幂等键提交。超时但可能成功时先查询执行记录，禁止盲目重试。
7. 结果经业务规则校验，保存产物与证据；提交任务状态和 outbox 事件；前端通过带序号事件恢复显示。
8. 记录脱敏追踪、费用、人工修改和业务反馈。用户取消停止后续工作，但已产生的外部副作用需要补偿流程。

## LangGraph 与 Temporal 如何分工

LangGraph 适合图内状态、上下文、暂停和检查点；Temporal 适合跨服务、长时间等待、重试和业务生命周期。[S45][S30]

补充：以统一 Runtime 接入多个 Harness 时，先逐个声明各实现的恢复和拦截能力；消息重建不能自动替代框架内部状态与业务动作对账。

若同用：Temporal 拥有外层业务任务状态，Activity 调用有界 Agent 子任务；子任务拥有独立 subrun_id。重试先按 subrun_id 查完成记录。模型调用置于 Activity 或受控执行层，避免工作流重放触发新的模型请求。不要让两套引擎同时决定同一个业务动作是否重试。

如果只需要短任务或单图恢复，先用一种状态所有者。检查点和 durable execution 都不能单独保证外部副作用“恰好一次”；数据库唯一约束、业务幂等与对账仍然必需。
