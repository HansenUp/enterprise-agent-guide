# 32 语言、框架与开源项目选型矩阵

## 开发语言：按边界选择

| 层 | 默认建议 | 替代条件 | 不建议的做法 |
|---|---|---|---|
| AI 编排、评测、数据处理 | Python + 类型校验；FastAPI 服务接口 | 全栈 TypeScript 团队可沿用 JS/TS SDK；JVM 团队评估 Spring AI/LangChain4j | 为追求“统一语言”重写成熟业务系统 |
| 产品交互 | TypeScript + React，优先沿用企业设计系统 | 已有 Vue 等体系直接复用 | 把模型密钥或权限判断放前端 |
| 业务控制面与工具适配 | 现有 Java/Spring Boot、.NET 或 Python | 新平台以团队维护能力决定 | 一开始同时引入四种后端语言 |
| 高并发基础组件 | 直接采用成熟网关、推理和队列项目 | 只有性能瓶颈证据充分才用 Go/Rust 定制 | 用语言性能口号替代链路分析 |

FastAPI 提供类型驱动的接口开发与 OpenAPI 能力，但业务授权、持久化任务和故障恢复仍需平台实现。[S56]

## Agent 框架：同一层通常只选一个主框架

| 选择 | 推荐用途 | 必须验证 | 替代或退出方式 |
|---|---|---|---|
| 显式状态机 + 模型 SDK | 固定流程、少量工具、低依赖 | 有界循环、错误分类、预算与状态保存 | 保留业务契约，后续换编排器 |
| LangGraph | 复杂有状态流程，显式图、检查点和人工中断 | 存储后端、恢复语义、副作用重复、版本升级 | 核心业务工具不耦合图对象 [S45] |
| Claude Agent SDK | 需要现成工具循环与 Hooks 的应用候选 | 按具体版本验证工具控制、子任务、会话和部署边界 | 独立运行契约与恢复等级 [S68] |
| Pydantic AI | Python 类型化输入输出、较轻量的 Agent 服务 | 目标模型能力、工具行为与持久化需求 | 独立工具协议、结构化输出契约 [S46] |
| Spring AI / LangChain4j | JVM 原生系统，团队不希望新增 AI 服务语言 | 模型接入、工具、RAG、追踪与状态治理 | 用接口隔离框架，避免同时采用两套 [S36][S37] |
| Microsoft Agent Framework / Google ADK | 已采用对应生态且平台集成收益明显 | 当前 SDK 语言、版本成熟度、运行环境与迁移 | 先做兼容性验证，外置任务与工具契约 [S10][S39] |
| Dify | 可视化构建和部门应用试验 | 授权粒度、发布审核、数据迁移、许可证 | 用受控 API 接业务能力，不直接开放数据库 [S60] |

“多 Agent”不是框架选择理由。先比较单 Agent、固定工作流与多 Agent 在同一任务集上的质量、人工成本与延迟。框架自带 UI、商业托管版和社区 SDK 也不能混为同一产品。

## 数据、能力与治理组件

| 环节 | 默认建议 | 何时采用替代方案 | 验收重点 |
|---|---|---|---|
| 关系数据与初期向量检索 | PostgreSQL + pgvector | 独立向量扩容需求选 Qdrant；强全文/复杂混合搜索选 OpenSearch | 权限过滤后召回率、更新删除、一致性与 p95 [S47][S48][S57] |
| 文档解析 | Docling，难例增加专门 OCR/表格服务 | 已有文档中台优先复用 | 扫描件、表格、阅读顺序、页码证据 [S49] |
| 模型网关 | 多提供方时评估 LiteLLM；单提供方可薄适配 | 企业已有 AI 网关时复用 | 预算、路由、请求差异、审计脱敏；企业功能另核 [S50] |
| 自托管推理 | vLLM | SGLang 做同模型同硬件对照 | 工具调用、结构化输出、长上下文、吞吐与显存 [S33][S62] |
| 身份 | 企业现有 SSO；无统一体系时 Keycloak | 托管 IdP | 用户身份与工具委托权限不能混同 [S52] |
| 策略 | 简单策略用服务端代码；跨服务规则再引入 OPA；应用授权可评估 Cedar | 资源关系复杂时另评估关系授权引擎；审批状态由平台管理 | 默认拒绝、规则版本与策略失效 [S53] |
| 遥测与 LLM 追踪 | OTel + 现有监控；Langfuse 作 LLM 追踪候选 | 既有平台或其他符合需求的追踪工具 | 数据脱敏、留存、跨链路关联和运行成本 [S51][S58] |
| 评测 | pytest/任务断言 + 人工标注；Ragas 辅助 RAG 评测 | 自定义领域指标 | 自动评分不能替代业务正确性和权限测试 [S59] |
| 模型训练与资产 | 有微调或传统 ML 需求再评估 MLflow | 现有 MLOps 平台 | 数据版本、训练可复现、模型审批与回滚 [S63] |

对象存储、队列、缓存、CI/CD、密钥管理优先复用企业标准。没有既有标准时，可先采用托管 PostgreSQL、S3 兼容对象存储与云密钥服务；严格内网由基础设施团队提供同等能力。不要为了“全开源”临时拼装无人维护的存储集群。

## 基础设施的具体候选与默认边界

| 环节 | 推荐候选 | 采用条件与边界 |
|---|---|---|
| 后台任务分发 | 低负载可用数据库任务表；需要专门消息代理时 RabbitMQ | 确认消息、死信、幂等和重放；使用 Temporal 的任务调度时不重复引入同用途队列 [S64] |
| 缓存与短期计数 | Valkey | 用于短期缓存与限流候选；持久任务状态和最终费用账本留在数据库，验证客户端兼容 [S67] |
| 发布交付 | 企业现有 CI + Kubernetes 环境的 Argo CD | Git 中保存声明式配置；配置同步不能替代业务审批、数据库回滚与评测门禁 [S65] |
| 运行监控 | Prometheus + 企业现有可视化/告警系统 | 基础指标和 SLO；LLM 语义追踪另接追踪平台；避免每次新增组件都引入新仪表盘 [S66] |

这些候选补齐新建平台的基础组件入口；已有可靠同类设施时默认复用。每新增一个有状态服务，都要明确其备份、升级、容量、值班和恢复负责人。
