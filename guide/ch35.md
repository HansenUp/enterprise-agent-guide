# 35 评测、发布、可观测性与成本闭环

## 评测分层与发布门禁

| 层 | 评测内容 | 失败处理 |
|---|---|---|
| 契约 | JSON Schema、工具参数、超时和错误类别 | 阻断发布 |
| 知识 | 解析、权限过滤、召回、来源定位、引用与回答一致 | 分析数据/检索/生成各自责任 |
| Agent | 任务完成、工具序列、预算、循环、恢复与审批 | 比较基线；关键安全失败阻断 |
| 业务 | 核心结果正确性、人工修正、误操作损失 | 领域专家确认，不能由 LLM 单独验收 |
| 系统 | 并发、队列积压、依赖失效、租户越权、恢复 | 演练后修复，再小流量发布 |

Ragas 可辅助 RAG 指标；自动 judge 需用人工标注校准，记录 judge 版本、误判与置信区间。[S59] 首批评测集覆盖常规、边界、长尾和攻击样例；样本量按覆盖与统计要求确定，不能把“几百条”当充分性保证。

Release 固定代码、提示、模型、工具 schema、策略、知识快照和评测集版本。流程为提交 → 单元/契约检查 → 离线回归 → 安全测试 → 人工审批 → shadow → canary → 全量。回滚恢复整套 release；进行中的长任务保持原版本或明确迁移，不直接混用新旧图结构。

## 遥测与故障定位

同一 trace 关联网关、run、模型、检索和工具调用。OTel 用于统一追踪、指标与日志关联；采用现有监控系统，不另建一套孤立告警。[S58] Langfuse 可作为 LLM 追踪、评测与提示管理候选；自托管要评估配套存储、worker、升级与企业功能成本。[S51]

面板至少分开：用户请求成功率、业务任务成功率、人工接管率、依赖错误、首响应和总完成延迟、队列等待、token/费用、审批等待。长任务 SLO 不宜和聊天首字时间混合计算。日志按敏感等级采样和脱敏，事故证据保留也需授权。

## 成本与容量：可计算而非拍脑袋

月度模型成本 = 输入 token/百万 × 输入单价 + 输出 token/百万 × 输出单价 + 缓存/工具/嵌入等费用。平台总成本再加入基础设施、标注、研发运维与失败补救；单位成功成本 = 同一周期总成本 / 经业务验证的成功任务数。

演示假设：每日 10,000 次任务，每任务平均 3 次模型调用，每调用输入 2,000、输出 500 token，30 天约产生输入 18 亿、输出 4.5 亿 token。价格使用采购时有效报价；这是容量示例，不是业务预测。重试和多 Agent 会放大用量。

Little 定律估算在途量：到达率 2 任务/秒、平均耗时 20 秒，对应平均 40 个在途任务；突发、长尾和排队需额外压测。GPU 数量应由目标模型、上下文、量化和实测吞吐决定，不能由员工人数推算。

缓存不得跨权限复用；预算在平台账本预留并结算，不能只依赖提供方最终账单。超过预算优先停止新增调用或转人工；降低模型质量前重新确认该类任务的能力下限。
