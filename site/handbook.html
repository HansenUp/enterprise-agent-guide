01 使用方法与共同基础

怎样学得快，又能讲清楚

不要同时安装十个框架。先选择一条主线，把统一项目做到可恢复、可观测，再用另一个框架复现关键步骤。Python 主线建议 LangChain → LangGraph；Java / Spring 主线建议 Spring AI → Spring AI Alibaba。AgentScope Python / Java 作为独立路线，与主线比较工具执行、工作区和服务治理。专项需求再选 LlamaIndex、PydanticAI 或其他框架。

每一轮学习形成四份证据：一张执行时序图、一段真实运行日志、一份失败案例表、一页 Architecture Decision Record（架构决策记录，简称 ADR）。面试时先说业务约束，再说实现位置，最后说验证结果。没有实测的数据，不写成自己的项目成果。

02 统一实战：企业知识问答与工单处理

项目输入与输出

构建一个 Support Agent（支持智能体）：检索企业政策、查询工单；证据不足时请求补充；需要创建工单时先形成草稿，经人工批准后提交。使用两个租户 A、B，各 20 篇虚构文档、10 张工单；其中 5 篇文档包含过期信息，2 篇包含“忽略原指令”的恶意文本。

工具契约统一为 search_policy(query)、get_ticket(ticket_id)、prepare_ticket(title, description)、commit_ticket(draft_id, approval_id)。tenant_id、user_id 由认证服务注入执行上下文，不能采用模型提供的租户身份。写入接口另由服务端传入幂等键。

认证与租户绑定 → 请求分类 → 知识检索 / 工单查询
                              ↓
                        带证据的答复
                              或
                      工单草稿 → 人工审批
                                   ↓
                         再鉴权 → 幂等提交 → 回执

这张图是业务流程设计，不代表十个框架都提供同名原语。高层 Agent 负责理解和选择工具，确定的身份校验、审批判定、幂等提交由应用服务保证。

评测集与失败注入

建立 60 条练习用例：20 条正确回答、10 条证据不足、10 条权限边界、10 条工具异常、10 条审批与重复提交。该数量用于学习，并不构成生产统计充分性。质量分别计算回答正确率、引用支持率、工具选择正确率、越权次数、重复提交次数、端到端 P95 延迟与每个成功任务成本。

测试至少覆盖：模型 429、检索超时、错误工具参数、工具响应非预期结构、审批过期、重复点击批准、会话 ID 被篡改、文档携带恶意指令、并发更新同一会话、升级后恢复旧状态。先用确定性工具和模拟模型验证流程，再用真实模型评测推理质量。

03 LangChain：标准 Agent 开发主线

定位与学习顺序

当前高层入口是 create_agent。先学 Model（模型）、Message（消息）、Tool（工具），再学 Middleware（中间件）和状态；复杂拓扑下沉到 LangGraph。LangChain Agent 基于 LangGraph，但两者不是同一抽象层。官方概览

建议 3 天：第 1 天跑工具循环与结构化输出；第 2 天加入会话与中间件；第 3 天完成故障测试，并解释何时需要自定义图。

核心机制逐项掌握

  1. **Model Adapter（模型适配器）**统一调用形式，但不同模型的工具调用、流式输出、上下文长度与 Schema 支持仍不同。切换模型必须重新评测，不能只改字符串就宣称完全兼容。
  2. **Message（消息）**承载用户输入、模型输出、工具调用与工具结果。工具结果必须对应正确的调用标识，不能随意删除一半工具消息。排查错误先打印脱敏后的消息结构，而不是只看最终文本。
  3. **Tool Schema（工具结构定义）**通过参数类型和描述说明用途。描述讲清适用条件、单位、边界；真正的权限与业务校验放在工具服务。优先使用小而明确的工具，避免一个“万能操作”函数。
  4. **Agent Loop（智能体循环）**反复调用模型、执行工具、回传观察，直到生成最终回复或达到限制。设置最大调用次数、总时长和预算，避免反复检索同一问题。
  5. **Middleware（中间件）**在模型或工具调用周围处理上下文、重试、日志和策略。顺序决定行为：鉴权应在执行前，日志脱敏应在写出前，重试不能吞掉审批拒绝。机制与扩展点
  6. **Short-term Memory（短期记忆）**保留线程状态；**Long-term Memory（长期记忆）**存储跨会话可检索信息。持久化、摘要和检索分别解决不同问题，不能把历史全塞入 Prompt。

最小教学示例

先按官方 Quickstart安装框架及选定模型提供方的集成包。MODEL_ID 使用该集成支持的模型标识，相关密钥按提供方设置。以下示例为原创教学代码，未完成依赖安装与联网运行验证；数据为模拟数据。

import os
from langchain.agents import create_agent

def get_ticket(ticket_id: str) -> str:
    """Look up a demo ticket by its exact identifier."""
    records = {"T-001": "status=open; category=network"}
    return records.get(ticket_id, "not_found")

agent = create_agent(
    model=os.environ["MODEL_ID"],
    tools=[get_ticket],
    system_prompt="查询工单时使用工具；不存在就说明未找到。",
)
result = agent.invoke({
    "messages": [{"role": "user", "content": "查询 T-001 的状态"}]
})
print(result["messages"][-1].content)

解释：函数是工具执行端；create_agent 组织循环；invoke 传入消息状态。返回文本本身不能证明调用过工具，需检查中间消息或轨迹。这个例子没有持久会话、权限和线上工单写入。

递进练习与排错

  • 练习 A：增加 T-999 不存在案例，要求保留 not_found 语义。验收：不能编造工单状态。
  • 练习 B：将工具改为第一次超时、第二次成功，给只读工具最多一次重试。验收：重试轨迹清晰，超出预算停止。
  • 练习 C：加入返回字段校验及会话状态。验收：不同会话互不污染，JSON 格式与业务值分别验证。
  • 练习 D：通过中间件控制工单提交审批。验收：直接调用工具服务也不能绕过服务端审批校验。

模型不调用工具时，先检查模型能力、工具是否绑定、描述是否清楚，再检查提示词。输出结构错误时区分提供方原生约束与应用解析。中间件“没生效”时检查挂载层级、执行顺序与子 Agent 是否走同一路径。

面试自测

Q1 · LangChain 与 LangGraph 如何选择？

**参考答案：**标准工具循环先用 LangChain，以较少代码获得模型、工具和中间件组合；有明确分支、并行汇总、审批恢复或自定义状态需求时使用 LangGraph。可以把 LangChain Agent 作为图中的节点。决策依据是控制需求和调试成本，不是“新框架替代旧框架”。**追问：**为什么不一开始全部写图？答：会增加状态、边界和路由维护成本，应由业务复杂性证明这笔成本必要。

Q2 · Function Calling 能保证业务正确吗？

**参考答案：**它只表达调用意图和参数。执行器仍需校验类型、枚举、权限、数据归属、业务约束与重复操作。结构正确的金额也可能不合法。**追问：**工具参数含 tenant_id 怎么办？答：不以模型参数作为身份，使用服务端认证上下文覆盖并校验资源归属。

Q3 · 怎么防止 Agent 无限循环？

**参考答案：**设置总轮数、时长、Token 与工具预算，识别重复无进展调用，提供明确的证据不足出口。预算耗尽时返回可解释的未完成状态。**追问：**是不是温度设为零就可以？答：不能，采样控制不提供终止性保证。

Q4 · 怎样做模型切换？

**参考答案：**统一适配层只解决接口；还要用同一数据集验证工具选择、参数、结构化输出、历史消息兼容、成本和延迟。切换前保存版本与回滚配置。**追问：**工具行为不兼容？答：在适配层处理差异或限制共同能力集，避免把所有差异藏在 Prompt 中。

Q5 · 如何设计 Middleware 的顺序？

**参考答案：**先明确每个扩展点包围的是 Agent、模型还是工具。把身份与策略放在动作之前，日志脱敏放在导出之前；重试只覆盖允许重放的调用。测试嵌套顺序及异常传播。**追问：**自动重试写工具？答：只有业务幂等和结果确认机制成立后才允许。

04 LangGraph：状态、控制与恢复

定位与学习路径

LangGraph 适合把执行过程显式建模。图允许循环，不只是 DAG（Directed Acyclic Graph，有向无环图）。先用确定性函数学习图，再接入 LLM（Large Language Model，大语言模型），能避免把模型不确定性误认为编排错误。Graph Quickstart

建议 4 天：状态与路由一天；并行与 Reducer 一天；中断和持久化一天；故障恢复与发布迁移一天。

必须真正理解的机制

  • StateGraph（状态图）：定义共享状态与节点连接。节点返回状态更新，而不是随意修改全局对象。让业务 ID、阶段、证据、审批引用可独立查看。
  • Node（节点） / Edge（边）：节点执行任务，边控制下一步；Conditional Edge（条件边）依据状态选择路径。模型负责开放式判断，规则节点负责硬约束。
  • Reducer（归并函数）：同一字段收到多个更新时如何合并。追加列表、覆盖值、按 ID 去重是不同语义。并行汇总需考虑顺序、重复与冲突，不应盲目给所有字段设置列表追加。
  • Checkpoint（检查点）：保存运行状态与执行信息，支持后续恢复或查看。生产应使用适当的持久存储；内存保存仅用于练习。thread_id 用于关联状态，不是授权凭证。Persistence
  • Interrupt（中断）：等待外部输入，恢复时通过 Command 提供结果。恢复可能重新执行所在节点的前半段，不能把不可重复的副作用随意放在中断前。Interrupts
  • Subgraph（子图）：封装阶段或子 Agent，需定义输入输出和状态作用域。子图不应依赖父图所有内部字段。Subgraphs
  • Functional API（函数式接口）：用函数组织执行逻辑，是图 API 之外的表达方式。选型看团队对显式拓扑、函数组合与调试方式的偏好。Functional API

不依赖模型密钥的状态图示例

安装目标版本 langgraph 后可尝试运行。下列教学代码没有调用模型，也不模拟实际审批；目的是看清状态如何决定路径。本文仅检查代码语法，未在框架运行环境实测。

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict, total=False):
    question: str
    needs_ticket: bool
    status: str

def classify(s: State):
    return {"needs_ticket": "报修" in s["question"]}

def route(s: State):
    return "draft" if s["needs_ticket"] else "answer"

builder = StateGraph(State)
builder.add_node("classify", classify)
builder.add_node("draft", lambda s: {"status": "awaiting_approval"})
builder.add_node("answer", lambda s: {"status": "answered"})
builder.add_edge(START, "classify")
builder.add_conditional_edges("classify", route,
                              {"draft": "draft", "answer": "answer"})
builder.add_edge("draft", END)
builder.add_edge("answer", END)
app = builder.compile()
print(app.invoke({"question": "我要报修网络"}))

预期状态含 needs_ticket=True 与 status=awaiting_approval。这里 END 只是本次图运行结束，“等待审批”只是业务字段；下一步必须实际接入 Interrupt 和 Checkpointer（检查点保存器），才是可恢复暂停。不要把命名成“等待”误当成框架挂起机制。

递进实验

  1. 将关键词分类替换为模型结构化分类，保留规则兜底。验收：模型解析失败有确定出口。
  2. 增加政策与历史工单两个并行节点，按证据 ID 去重。验收：乱序和重复输入下汇总结果一致。
  3. 依据官方 Interrupt 示例加入审批与持久 Checkpointer。验收：暂停后关闭进程，重启后用同一业务关联恢复。
  4. 在模拟提交后、写检查点前故意失败。验收：再次运行不会生成重复工单；解释为什么靠检查点不够。
  5. 保存旧状态后新增一个字段并升级。验收：旧状态能迁移或明确隔离到旧运行版本，不直接用新图恢复所有历史线程。

面试自测

Q1 · Checkpoint 能保证 Exactly-once（恰好一次）吗？

**参考答案：**不能独自保证外部动作恰好一次。外部工单服务成功后，本地状态可能没保存；恢复可能重放。需要稳定业务幂等键、结果查询和副作用账本，必要时使用事务消息。**追问：**能否每次重试生成新键？答：不行，同一逻辑操作必须复用键。

Q2 · 为什么并行节点更新出错？

**参考答案：**检查是否同时写同一字段以及该字段的归并语义。设计独立输出或使用正确 Reducer；关键事实不能用最后写入覆盖掩盖冲突。**追问：**列表相加足够吗？答：要看是否要求去重、顺序和来源追踪。

Q3 · Interrupt 前为什么要谨慎放副作用？

**参考答案：**恢复时节点代码可能从开头重新运行，之前的外部操作可能再次发生。把不可重复操作移到审批后的独立步骤，并通过业务幂等控制。**追问：**中断是否保存 Python 调用栈原地续跑？答：不应这样理解，它依赖框架的持久状态与重执行语义。

Q4 · thread_id 能直接使用前端参数吗？

**参考答案：**可以作为请求参数接收，但必须由服务端校验与用户、租户的绑定；不能把猜到 ID 等同于有权恢复。并发写同一线程还需冲突策略。**追问：**两个审批同时到达？答：按审批状态做原子更新，过期或重复结果返回明确状态。

Q5 · 什么时候还要企业工作流引擎？

**参考答案：**跨系统长事务、定时补偿、长期 SLA 和复杂人工作业，可能需要企业持久工作流承接业务生命周期。Agent 图负责智能决策阶段。明确谁重试和谁持有业务真相，避免双重编排。**追问：**能全由图实现吗？答：可以工程实现部分能力，但要比较运维和正确性成本。

核心概念与职责

**Agent（智能体）**组织模型与工具循环。**Toolkit（工具集）**提供可调用能力；把查询、草稿、提交分开注册，减少混淆。**Model Adapter（模型适配器）**封装提供方差异。**Middleware（中间件）**调整上下文或执行行为。**Event（事件）**使过程可被消费和展示；事件日志、业务审计和恢复状态是不同数据，不应只存最后一段回复。

**Workspace（工作区）**承载任务文件与产物；**Sandbox（沙箱）**限制执行环境。工作区目录不是安全边界，真实隔离还依赖后端和部署策略。**Permission（权限交互）**用于表达执行许可，企业仍需将登录身份、租户策略、审批范围连接到它。

2.x 提供 Agent Service、Agent Team 等服务化和协作方向。具体权限行为、持久化范围和部署接口应逐项在稳定版验收，开发文档只能用于了解演进方向。Agent Service · 开发文档、Agent Team · 开发文档

从官方示例改造成项目

  1. 在独立环境安装选定的 2.x 发行版，运行该版本 README 或示例中的最小 Agent。记录实际 import、模型配置和响应事件；先不要加入服务层。
  2. 替换为 get_ticket 只读工具，返回可验证的虚构状态。工具代码只做查询，模型不持有数据库凭据。
  3. 加入查询政策工具，限制结果长度；大结果保存为工作区产物，并只给模型摘要与引用。验收：引用指向正确文件或记录，压缩后仍保留关键限制。
  4. 接入工具执行前的权限处理。用批准、拒绝、超时三类事件驱动状态，拒绝不被当成可重试网络错误。Permission · 开发文档

上下文与协作实验

把工具结果扩大到原来的 100 倍，比较截断、摘要、外置引用三种方案。记录 Token、引用正确率和遗漏率。不要只看“省了多少 Token”，摘要丢掉禁止条件可能导致更严重错误。

单 Agent 跑通后增加 Worker（工作 Agent）：只接收任务目标、必要证据、截止时间和允许工具，输出结构化结论与引用。Leader（协调 Agent）汇总时检查冲突，不要求所有工作者共享完整历史。验收：Worker 失败时能降级或显式失败，不能无限互相委派。

生产练习与典型坑

把模型调用和数据库事务分开。不要开启数据库事务后等待模型几十秒；先读取必要快照，智能阶段生成建议，提交阶段用短事务重新校验业务条件。审批期间业务数据可能已变更，应通过版本号或条件更新防止提交过期草稿。

SSE（Server-Sent Events，服务器发送事件）断开时区分取消展示与取消后台任务。为任务定义运行、等待审批、成功、失败、取消等状态，并提供查询接口。异步执行时验证认证上下文是否正确传递，不默认线程局部变量跨线程有效。

Q1 · Spring AI Alibaba 与 Spring AI 如何分工？

**参考答案：**Spring AI 提供基础 AI 接口与集成，Alibaba 增加 Agent / Graph 等编排能力。基础调用不必强行进入图；需要显式复杂流程时再使用图。**追问：**引入 Alibaba 是否必须换所有基础组件？答：按兼容依赖组合与业务需要集成，不是自动全量替换。

Q2 · 为什么不要在事务里等待模型？

**参考答案：**模型延迟与重试不可控，长事务占连接和锁，增加冲突。拆成读取、智能处理和短事务提交，提交时重新校验版本与权限。**追问：**一致性怎么办？答：用条件写入、版本检查或补偿流程，而不是一直持锁。

Q4 · 为什么模型调用被重试了很多次？

**参考答案：**检查 HTTP 客户端、模型适配器、拦截器、图节点和任务队列的重试叠加。统一总预算与重试责任，按错误分类。**追问：**429 应无限重试吗？答：不能，遵循退避和期限，超过预算降级或失败。

Q5 · 如何向前端设计流式响应？

**参考答案：**区分内容增量、工具状态、审批请求、最终结果和错误事件，用任务 ID 关联。断连后能查询最终状态，写操作不能因页面重复连接而重复执行。**追问：**Token 流结束就是任务成功吗？答：不是，可能还在工具执行或提交阶段。

概念拆解

**Harness（运行支撑层）**把常见执行周边能力组织起来；HarnessAgent是相应高层入口。agentscope-harness 与较底层 agentscope-core 不是完全等价模块；模型提供方有独立扩展依赖。学习时画出依赖图，避免把高层内置能力误认为底层类默认具备。

Q1 · HarnessAgent 与底层 Agent 怎么选？

**参考答案：**任务文件会增长，也可能包含敏感内容。需要配额、过期清理、归属、产物保留和失败任务清理策略。**追问：**删工作区会影响恢复吗？答：可能，需区分临时文件与恢复依赖的持久产物。

定位与核心模型

LangChain4j 是独立 Java 生态，不是 Python LangChain 的逐行翻译。学习从 AI Services（人工智能服务）开始：用 Java 接口描述能力，由框架组织输入、模型调用和输出转换。然后学习 ChatMemory、Tools、RAG 和结构化输出。AI Services

建议 2 天完成基础项目。先按官方入口选择模型集成和发行版；语言、框架集成、模型模块统一锁定。官方将早期 Chains 标为 legacy，新学习不把 ConversationalChain 作为唯一入口。

必学概念与练习

  • AI Service（AI 服务）：接口是应用边界。先定义 String answer(String question)，再调整为带来源和是否转人工的返回对象；接口签名简洁不等于语义天然正确。
  • ChatMemory（聊天记忆）：给每个会话独立范围，控制窗口和持久化。会话历史管理不等于复杂业务执行恢复。
  • Tool（工具）：用明确 Java 类型和工具描述暴露查询；工具对象不应在成员变量中保存跨用户临时状态。
  • **Content Retriever（内容检索器）**与 Retrieval Augmentor（检索增强器）：理解检索发生在哪、结果如何进入模型，以及身份过滤在哪一层落实。
  • Structured Output（结构化输出）：映射对象前后都要校验，不能把“能反序列化”作为答案正确的证据。

上手任务

复制目标版本官方 AI Services 最小工程，先跑无记忆调用。第二步把 TicketQueryService 注册为工具；第三步为两个用户配置不同记忆；第四步加入政策检索；第五步模拟结构化解析失败和工具超时。分别保存模型消息、工具日志与最终对象。

验收：A 会话看不到 B 历史；未知工单返回未找到；输出对象来源可回溯；无权限文档不进入检索结果。若增加多 Agent 或持久编排，另查目标版本 Agentic 模块，不把 AI Services 接口代理本身当完整业务工作流。

面试自测

Q1 · AI Services 帮开发者省掉了什么？

**参考答案：**它组织接口输入输出与模型交互，并可组合记忆、工具和检索，减少样板代码。业务授权、质量评测和副作用一致性仍由应用设计。**追问：**会不会隐藏错误？答：需要保留底层调用轨迹和明确异常边界。

Q2 · LangChain4j 和 Spring AI Alibaba 如何选？

**参考答案：**先比较声明式 AI 服务是否满足需求，再比较显式图、Spring 集成、状态恢复及团队习惯。使用同一项目对照，避免按名字相似度决定。**追问：**能同时使用吗？答：可以，但模型、工具、状态层重复抽象会增加成本，应明确边界。

Q3 · ChatMemory 为什么不能作为长期知识库？

**参考答案：**对话记忆侧重交互上下文，长期知识需要更新、检索、权限、来源与删除能力。所有历史进入模型会增加成本且引入陈旧信息。**追问：**用户偏好放哪？答：经确认后进入有归属、时间和可删除策略的长期存储。

Q4 · 返回 Java 对象就能避免幻觉吗？

**参考答案：**不能，对象只约束结构，事实需由证据、工具查询与业务规则验证。**追问：**枚举值正确但结论错误？答：评测语义正确性和来源支持，而非只检查反序列化成功。

Q5 · 为什么单例工具对象可能串数据？

**参考答案：**如果把当前用户或临时结果放在可变成员字段，并发调用会互相覆盖。使用无状态工具和显式调用上下文。**追问：**线程安全集合能解决吗？答：还需正确的租户键、生命周期与授权，容器线程安全不等于隔离正确。

09 PydanticAI：类型、依赖和可测试性

定位与概念

PydanticAI 适合希望用 Python 类型表达依赖、工具输入和输出约束的团队。核心学习对象是 Agent、Dependencies（依赖）、RunContext（运行上下文）、Output Type（输出类型）和 Validation（校验）。类型有助于发现接口错误，但不能证明业务事实正确。Agent 官方文档

建议 2 天：第一天类型化输入输出与工具，第二天依赖注入、失败校验、测试与预算。按官方概览建立独立项目并锁定版本；API 字段在版本演进中可能变更，尤其不要无检查地混用旧教程的结果字段与当前 Output 接口。

  1. 用 Pydantic 数据模型定义 SupportAnswer，包含 answer、sources、needs_human；用必填字段与枚举表达结构约束。
  2. 定义依赖对象，传入工单服务、知识查询服务和可信用户上下文。模型只看到工具输入 Schema，不应自行构造授权身份。
  3. 注册读取依赖的工具。跟踪一轮调用，解释 RunContext 如何把应用依赖送到工具实现。
  4. 添加业务输出校验：sources 必须来自本次检索，工单状态必须来自工具。错误按类别处理：可修复格式问题允许有限重试，权限拒绝直接终止。
  5. 使用官方测试支持或自建确定性替身测试流程，再接真实模型检查工具选择。保存每次尝试，避免只统计最后成功输出。

面试自测

Q1 · Type Safety（类型安全）解决不了什么？

**参考答案：**不能证明事实、权限与推理结论正确。它约束数据结构和程序接口；还要有运行时业务校验与评测。**追问：**为什么仍值得用？答：减少边界错误，改善重构、测试和故障定位。

Q2 · Dependencies 和 Prompt 中写用户身份有何区别？

**参考答案：**依赖把可信应用对象传入工具，Prompt 是模型可见文本，不能作为安全执行环境。**追问：**权限从哪里读？答：从认证后绑定的依赖或服务端上下文读取，并校验资源归属。

Q3 · Validation Retry（校验重试）有哪些风险？

**参考答案：**可能增加成本和时延，掩盖错误输出率，或者导致重复副作用。限定次数，记录首轮成功率，区分模型修复与工具重试。**追问：**一次任务成功率怎么计算？答：同时报告最终成功率、尝试次数和总成本。

Q4 · 怎么测试不用真实模型也有价值？

**参考答案：**用确定性替身验证路由、依赖、预算、解析、权限和异常传播；真实模型负责补充验证推理与工具选择。**追问：**Mock 测试能代表线上质量？答：不能，两类测试目的不同。

Q5 · 什么时候需要额外编排层？

**参考答案：**当任务跨多个确定阶段、审批等待和持久恢复边界时，评估相应图或持久工作流能力；不要把单 Agent 输出校验当全过程状态管理。**追问：**必须引入 LangGraph 吗？答：不是，按现有栈与所需恢复语义选型。

10 LlamaIndex：以数据与检索为中心

定位与学习地图

先学数据进入系统到回答生成的完整链路，再学 Agent。重点是 Document（文档）、Node（文本节点）、Transformation（转换）、Index（索引）、Retriever（检索器）、Query Engine（查询引擎）及 Response Synthesis（回答合成）。LlamaIndex 也有 Agent / Workflow 能力，不能仅称为向量库包装。学习总览、官方入口

建议 3 天：摄取与索引一天；检索评测一天；查询工具与工作流一天。模型、Embedding（向量嵌入）与向量存储按实际需要选择集成包，先锁定基础可用组合。

必须理解的链路

Document 保存原始内容与元数据；Node 是切分后参与检索的单位，应保留来源和位置。Index 提供组织与访问方式，Retriever 找候选证据，后处理可做过滤与重排，Query Engine 组织查询和生成。Agent 则可按任务选择不同查询工具。

RAG 的质量不是只调模型：解析错误、切块丢上下文、过滤错误、召回遗漏、重排偏差、生成失真都可能出错。按阶段记录指标，能快速定位究竟该改哪个环节。

上手路线与验收

  1. 导入 20 篇虚构政策，保留 tenant、effective_date、document_id、version 元数据；先查看切分结果，不急着聊天。
  2. 创建索引并做纯检索，对 10 个问题人工标注应出现的证据。计算 Recall@k（前 k 个结果的召回率），解释 k 变大带来的上下文成本。
  3. 接入生成，返回引用和证据不足标识。验收：来源能定位原文，过期政策不被优先引用。
  4. 将查询引擎作为只读工具供 Agent 调用；同时保留工单工具。验收：政策问题和工单问题选择正确数据源。
  5. 删除或更新一篇政策，验证索引同步、缓存和引用失效处理；加入租户过滤及恶意文档测试。

面试自测

Q1 · Index、Retriever、Query Engine 怎么区分？

**参考答案：**索引组织数据，检索器返回候选上下文，查询引擎把检索和生成组合成回答流程。它们可分别替换和评测。**追问：**为什么先测检索？答：证据根本没取到时，调回答 Prompt 通常不是根本解决办法。

Q2 · Chunk Size（切块大小）越大越好吗？

**参考答案：**大块保留上下文但可能稀释匹配、增加 Token；小块更精确但可能失去完整语义。按文档结构和问题集实验，并考虑父子块或相邻上下文。**追问：**统一固定长度适合所有文档吗？答：不适合表格、条款和长段落等不同结构。

Q3 · 向量相似度高是否代表答案可信？

**参考答案：**相似只说明检索相关程度，不证明版本有效、权限正确或结论被支持。需要元数据过滤、引用验证和拒答机制。**追问：**置信阈值能通用吗？答：不能，不同模型、索引和语料分布需要校准。

Q4 · 多租户过滤放在生成后可以吗？

**参考答案：**不行，未授权内容已可能进入上下文、日志或缓存。应在数据访问与检索阶段强制过滤，并覆盖所有检索路径。**追问：**向量库不支持过滤？答：使用独立索引或其他能保证隔离的检索设计。

Q5 · 如何评估 RAG 的改进？

**参考答案：**分开测召回、证据有效性、答案正确性、引用支持和成本，再看端到端任务成功。固定测试集并加入更新时间与权限边界。**追问：**只测答案相似度够吗？答：不够，同义答案可能正确，措辞相似也可能事实错误。

11 CrewAI：角色协作与任务流程

定位与概念

CrewAI 适合以角色和任务分工组织协作的学习路线。先理解 Agent（智能体）、Task（任务）、Crew（团队）和 Process（执行过程），再学习 Flow（流程）以组织更明确的应用逻辑。角色描述不是组织权限，多个角色也不必然提高质量。Agents 官方文档、文档入口

建议 2 天。文档入口本次跳转到带版本页面，使用与安装版本一致的示例和命令；不要假定 latest 永远与本地版本一致。

如何设计协作

为研究者分配政策检索，为审查者分配引用核对，为汇总者分配最终回答。每个任务写清输入、期望输出、可用工具、完成标准和失败出口。只说“你是一位专家”无法替代任务契约。

先顺序运行，检查信息传递；再考虑并行执行独立任务。共享内容保留必要证据，不默认复制全部聊天记录。协调者应依据证据解决冲突，不能以多数投票替代事实验证。

上手练习

  1. 按官方入门创建一个 Agent 和一个 Task，只回答政策问题。
  2. 增加审查 Task，输出 supported / unsupported 及引用 ID；检查失败后转人工，不无限要求另一个 Agent “再想想”。
  3. 参考Flow 官方指南，用 Flow 组织输入检查、Crew 执行和最终校验；确定步骤与开放式任务分开表达。
  4. 对同一 60 条数据集比较单 Agent 与两 Agent。总 Token、时长预算一致，统计正确率与成本。
  5. 注入一个 Worker 超时和一条错误证据。验收：明确失败状态、不重复执行写工具、不把未完成任务包装为全部成功。

面试自测

Q1 · Agent、Task、Crew、Flow 分别是什么？

**参考答案：**Agent 表达执行角色和能力，Task 表达工作目标和输出，Crew 组织多角色任务，Flow 组织应用流程与状态控制。具体接口以版本为准。**追问：**是否每个节点都需要 Agent？答：规则校验和字段转换直接用程序更容易验证。

Q2 · 角色越多是否越专业？

**参考答案：**不一定，角色重叠增加协调和上下文成本。拆分必须有独立能力或并行收益，并用同预算实验验证。**追问：**两个 Agent 相互认可就可信？答：共享模型和证据可能导致相关性错误。

Q3 · Task 的期望输出怎样写？

**参考答案：**定义字段、证据、完成条件和失败表达，而不是“给出高质量报告”。必要时加程序校验。**追问：**返回格式正确但任务没完成？答：增加语义验收和工具轨迹验证。

Q4 · 如何控制协作成本？

**参考答案：**限制委派深度、单任务预算和总轮数，只传必要上下文，对重复检索做有权限隔离的缓存。**追问：**缓存所有回答是否安全？答：必须考虑租户、数据版本和失效，不能跨权限复用。

Q5 · 多 Agent 对话日志能直接做审计吗？

**参考答案：**日志有助调试，但审计还需可信身份、动作参数、授权记录、结果和时间关联。模型自述不等于执行事实。**追问：**审查 Agent 说“已审核”够吗？答：需要可验证的审查结果与执行记录。

12 Google ADK：Agent、Runner 与 Session

定位与学习入口

ADK（Agent Development Kit，智能体开发工具包）提供 Agent 开发与运行相关抽象。先选择一种语言路线，按官方快速开始建立工程，再学习工具、执行器、会话、事件和组合。不同语言 SDK 的能力与示例不假定完全一致。Get Started、官方入口

建议 2 至 3 天，本文练习以 Python 心智模型为主。先理解本地开发，再讨论具体云部署；不能把本地 SDK 能力和云平台托管能力合并为一张默认能力清单。

核心学习点

**Agent（智能体）**描述能力与行为；**Runner（执行器）**组织调用生命周期；**Session（会话）**记录交互相关信息；**State（状态）**承载任务变量；**Event（事件）**表达运行期间的消息或变化。学习时跟踪一次输入如何经过 Runner 到工具，再如何形成事件和状态更新。

**Artifact（产物）**适合保存任务生成的文件等内容；**Memory（记忆）**用于后续可检索信息，不能把所有产物文本当作永久 Prompt。**Callback（回调） / Plugin（插件）**用于扩展，调用前、调用后和错误路径需分别验证。

上手练习

  1. 按所选版本和语言官方 Quickstart 运行一个本地 Agent，用 get_ticket 替换示例工具。
  2. 建立两个独立 Session，观察事件和状态变化。验收：同一会话能接续，不同会话不串数据。
  3. 加入检索子 Agent 与汇总步骤，明确传入哪些状态。验收：子任务输出有可验证引用，父任务不误判失败为成功。
  4. 使用回调或插件增加工具预算和脱敏记录，并保留服务端权限校验。
  5. 选择目标持久 Session 服务，测试进程重启、并发请求和状态迁移；随后再评估部署平台对认证、监控和扩缩容的支持。

面试自测

Q1 · Agent 和 Runner 怎么区分？

**参考答案：**前者定义行为，后者组织执行及相关服务的协作。理解这个分层有助于替换会话存储、消费事件和处理运行错误。**追问：**为什么只看最终回复不够？答：无法判断工具调用、状态变更与失败发生的位置。

Q2 · Session、State、Memory 如何划分？

**参考答案：**Session 是交互范围，State 是该范围或定义作用域内的数据，Memory 是可供后续检索的信息机制。具体作用域按 SDK 规定。Session / State / Memory 官方说明**追问：**都存在同一个字典中可以吗？答：练习可能方便，生产会难以控制生命周期、隔离和迁移。

Q3 · Callback 能否代替全部安全检查？

**参考答案：**不能。它可执行过程策略，但直接调用工具、子 Agent 或其他入口仍需后端授权。应测试所有路径是否覆盖。**追问：**Prompt Injection（提示词注入）怎么防？答：把检索内容作为不可信数据，限制工具并强制服务端权限与审批。

Q4 · 本地跑通就能直接部署到云吗？

**参考答案：**还需处理身份、凭据、网络、会话持久化、日志、资源和运行时兼容性。托管平台与 SDK 的责任应分别列出。**追问：**迁移其他平台最难什么？答：通常是持久状态、身份、工具网络和事件契约，而不只是模型字符串。

Q5 · 如何设计事件消费？

**参考答案：**区分中间文本、工具动作和最终状态，处理断连、重复事件与消费延迟。业务动作以任务状态或账本确认，不能看到一段文本就判定成功。**追问：**是否展示全部事件？答：仅展示适合用户的进度，内部敏感参数应脱敏或不暴露。

五道综合题

Q1 · 设计一个企业 Agent 能力平台，框架放在哪里？

**参考答案：**入口认证与租户管理在接入层；模型网关负责模型访问策略；Agent 框架负责任务内的理解、工具循环或图编排；工具服务负责业务授权与副作用；数据层负责带权限的检索；状态、审计与评测贯穿各层。框架是运行组件，不承担全部平台职责。**追问：**为何不把所有权限放 Prompt？答：Prompt 不能形成可靠执行边界。

Q2 · 如何避免框架锁定？

**参考答案：**稳定的是工具 HTTP / MCP 契约、业务数据 Schema、测试集和任务 API。框架内部状态与节点实现允许专用化，不强求最小公分母。把迁移成本集中在适配层和状态迁移。**追问：**是否需要先造统一 Agent SDK？答：先有两个实际实现再抽象，避免为假设需求做框架套框架。

Q3 · 如何定位一次任务失败？

**参考答案：**按请求 ID 追踪身份、检索证据、模型输入输出、工具参数、执行结果、状态更新和最终答复，确定首个偏差点。分别归因数据、模型、工具、编排和基础设施。**追问：**模型自述“工具失败”可信吗？答：以执行端结构化结果为准。

Q4 · 如何灰度发布新 Agent？

**参考答案：**固定工具契约和评测集，对新模型、Prompt、编排分别版本化；先离线回归，再对只读任务影子运行，随后有限流量灰度。涉及写操作时影子路径不得产生副作用。**追问：**回滚图版本后旧线程怎么办？答：按运行版本路由或执行受控状态迁移。

Q5 · 企业最应该统一什么？

**参考答案：**身份、工具授权、审计、模型访问、数据权限、评测标准和发布流程优先统一。不同业务可以使用不同 Agent 框架，但需满足相同平台契约。**追问：**统一框架能省多少？答：需结合培训、维护、迁移和重复设施实测，不提供未经验证的比例。

必会的语言机制

Object Model（对象模型）：变量绑定对象，赋值通常不复制。列表和字典可变；把默认参数写成 items=[] 会让多次调用共享对象。浅复制只复制外层，嵌套对象仍可能共享。Agent 状态若包含嵌套工具结果，随意修改可能污染其他步骤。

Scope and Closure（作用域与闭包）：理解局部、外层、全局和内置名称查找。循环中创建回调时注意晚绑定；需要把当时的值绑定进参数或工厂函数。不要把当前 tenant_id 放在模块级可变变量中。

Iterator / Generator（迭代器 / 生成器）：迭代器逐项提供数据，生成器用 yield 暂停并保留局部状态。适合分批读取文档和输出流，但生成器未被消费时其中代码可能尚未执行；提前退出时要考虑资源关闭。

Context Manager（上下文管理器）：用 with / async with 表达资源获取与释放。数据库会话、文件、HTTP 客户端都有生命周期。异常清理放在 finally 或上下文管理器，不依赖垃圾回收及时回收连接。

Decorator（装饰器）：函数定义后被包装，可用于工具注册与追踪。保留签名和元数据，避免工具 Schema 生成器只看到 *args, **kwargs。装饰异步函数必须正确 await，不能把返回的协程对象误当结果。

Exception（异常）：按可修复输入、权限拒绝、暂时故障、永久故障分类；使用异常链保留原始原因。不要 except Exception: return "成功"，也不要把所有异常都送回模型继续尝试。

官方精读：Python Tutorial、Data Model、contextlib。阅读任务：找到上述每种机制的示例，再在统一工单项目中指出一个使用位置。

Q1 · Python 赋值、浅复制和深复制有什么区别？

**参考答案：**赋值增加对象绑定；浅复制创建新的外层容器但共享内部引用；深复制递归复制可复制的内部对象。不能用深复制复制数据库连接或代替状态设计。**追问：**Agent 状态怎么更新？答：明确不可变边界和字段更新语义，仅复制需要独立的结构。

Q2 · 为什么不能用列表作为默认参数？

**参考答案：**默认参数在函数定义时求值，后续调用可能复用同一列表。用 None 作默认值并在函数内创建新列表。**追问：**dataclass 呢？答：可变字段用 default_factory，不要共享默认实例。

Q3 · Generator 能减少内存吗？

**参考答案：**可避免一次构建全部结果，但调用方若最终 list(...) 全部物化仍会占用内存；上游缓存与资源生命周期也要考虑。**追问：**流式接口用了 yield 就一定不卡？答：生成器内部仍可能执行阻塞 I/O 或重计算。

Q4 · 为什么工具装饰器要保留签名？

**参考答案：**工具注册、依赖注入和 Schema 生成可能依赖参数与注解。使用适当包装方式并检查最终签名。**追问：**只保留函数名够吗？答：还需签名、文档和异步调用语义。

Q5 · GIL 是否意味着 Python 不用考虑线程安全？

**参考答案：**不是。GIL（Global Interpreter Lock，全局解释器锁）不提供业务级原子性，复合操作与外部资源仍可能竞争；还有可释放 GIL 的扩展及 Free-threaded（自由线程）构建。**追问：**现在 Python 多线程能否并行？答：取决于解释器构建、扩展兼容与工作负载，不能背“永远不能”或“已经全面取消”。官方自由线程说明

15 Python 异步并发与网络调用

四种执行方式怎么选

类型 适用场景 主要约束
Coroutine（协程） 有异步接口的模型、HTTP、数据库 I/O 协作式调度；事件循环内不能长时间阻塞
Thread（线程） 接入阻塞 I/O 库，或明确释放 GIL 的扩展 线程数、共享状态；取消等待不等于终止线程
Process（进程） 纯 Python CPU 密集处理或隔离任务 进程启动、序列化与内存成本
Durable Worker（持久任务工作进程） 长任务、重试、跨进程恢复 任务投递、持久化与业务幂等另行设计

async def 调用生成协程对象；await 等待可等待对象；Task（任务）负责调度协程。仅仅定义成异步，不会把 CPU 计算自动放到其他核心。asyncio.run 用于程序顶层入口，已有事件循环的服务内部通常直接 await。

**TaskGroup（任务组）**表达一组相关任务的生命周期；**Semaphore（信号量）**限制进入某段代码的并发数量；**Timeout（超时）**限制等待；**Cancellation（取消）**要求协程配合处理。gather 仍有用途，并未被弃用；它与 TaskGroup 的异常与取消行为不能混为一谈。asyncio 官方文档

背压与预算设计

假设每个请求并发 5 个工具，服务接收 100 个请求，实际下游可达 500 个调用。单请求 Semaphore 只限制本请求，不限制全服务；进程内 Semaphore 也不限制其他进程。分层设置请求预算、实例连接池和跨实例配额，并限制队列长度。

每次工具调用至少区分连接超时、读取超时与总截止时间。上游剩余时间应向下传播，不能每次重试都重新获得完整预算。429、短暂网络错误可以按策略退避；输入错误、权限拒绝不能无脑重试。HTTPX 的连接复用依赖客户端生命周期，不要在热循环里每次新建 AsyncClient。HTTPX Async Support

可运行练习：有限并发与超时

第 20 章内嵌的 async_tools.py 只使用 Python 3.11+ 标准库，不需要模型密钥。它用虚构工具演示三种结果：成功、超时、输入错误；并限制同时执行的工具数量。此练习验证并发边界，不代表远程服务性能。

运行 python3 python_stack_lab/async_tools.py 查看结果；运行 python3 -m unittest discover -s python_stack_lab -v 检查成功、超时、取消与并发上限。先按第 20 章保存两个文件到 python_stack_lab 目录，再在其上级目录执行命令。

排错顺序

接口全部变慢先检查 Event Loop Lag（事件循环延迟），再看连接池等待、下游延迟、队列长度与 CPU。time.sleep、同步 HTTP、PDF 解析和大型 JSON 运算都可能阻塞异步路径。阻塞 I/O 可考虑 asyncio.to_thread，但这不保证任务取消后底层线程停止。CPU 密集计算需另选进程或计算服务。

面试自测

Q1 · await 是否表示并行执行？

**参考答案：**await 表示等待并允许调度其他任务，不自动创建并行任务。连续 await 两次通常顺序执行，需显式组织并发任务。**追问：**为何模型请求适合异步？答：大部分时间等待网络响应，可在等待期间处理其他工作。

Q2 · TaskGroup 与 gather 怎么选？

**参考答案：**相关子任务需要共同生命周期及失败传播时优先考虑 TaskGroup；收集一组结果时可使用 gather，但要了解它的异常处理与取消语义。**追问：**允许部分工具失败？答：在子任务内把预期可降级错误转成结构化结果，不吞掉取消或所有编程错误。

Q3 · Timeout 就意味着外部操作没发生吗？

**参考答案：**不意味着。可能外部提交成功但响应超时，需查询结果或使用稳定幂等键。**追问：**取消本地任务能撤回外部工单吗？答：不能自动撤回，需要独立的补偿或取消业务接口。

Q4 · 为什么并发越高吞吐反而下降？

**参考答案：**连接池、模型限额、数据库、CPU 或内存饱和后，排队和重试会放大延迟。逐步压测找容量，设置并发上限和背压。**追问：**把 Semaphore 设为 100 就能限制每秒 100 次吗？答：不能，它限制同时执行数量，不等于速率限制。

Q5 · 怎么正确处理取消？

**参考答案：**在 finally 释放资源，必要时捕获取消做清理后继续传播；不要把取消当普通失败重试。为关键业务动作记录明确状态。**追问：**为什么不能吞掉 CancelledError？答：会破坏调用方及结构化并发的生命周期预期。

16 Python 类型、数据校验与工程组织

三种机制不要混用

**Type Hint（类型注解）**供阅读和静态检查，不自动进行运行时校验。**dataclass（数据类）**适合应用内结构化数据，不默认验证输入。**Pydantic（数据校验库）**适合不可信输入、模型输出和配置边界，但字段合法仍不保证事实或权限正确。

Pydantic 的宽松模式可能转换输入；Strict Mode（严格模式）减少部分类型转换，但不同类型与 Python / JSON 输入路径仍有差别，应按字段测试。Strict Mode 官方说明

**Protocol（结构化接口协议）**让业务依赖工具服务接口而非某个框架类；**Generic（泛型）**表达输入输出类型关系；**TypedDict（类型化字典）**用于字典形状的静态约束。不要把 TypedDict 当运行时请求验证器。

Q1 · Python 有类型注解为什么还要 Pydantic？

**参考答案：**类型注解不自动拒绝运行时错误输入；Pydantic 校验外部数据并构造对象。静态检查与运行时检查互补。**追问：**内部函数都用 Pydantic 吗？答：不必，按不可信边界和开销选择。

async_tools.py：有限并发、超时与资源释放

"""Python 3.11+ standard-library lab; no network or model credentials."""
import asyncio
from dataclasses import asdict, dataclass
import json


@dataclass(frozen=True)
class ToolResult:
    ticket_id: str
    status: str
    value: str | None = None


class DemoTools:
    def __init__(self, concurrency: int = 2):
        if concurrency < 1:
            raise ValueError("concurrency must be positive")
        self.limit = asyncio.Semaphore(concurrency)
        self.active = 0
        self.peak = 0

    async def lookup(self, ticket_id: str, delay: float) -> str:
        if not ticket_id.startswith("T-"):
            raise ValueError("invalid ticket identifier")
        self.active += 1
        self.peak = max(self.peak, self.active)
        try:
            await asyncio.sleep(delay)
            return "open (simulated)"
        finally:
            self.active -= 1

    async def run(self, ticket_id: str, delay: float,
                  timeout: float = 0.2) -> ToolResult:
        try:
            # The deadline includes time waiting for a concurrency slot.
            async with asyncio.timeout(timeout):
                async with self.limit:
                    value = await self.lookup(ticket_id, delay)
            return ToolResult(ticket_id, "ok", value)
        except TimeoutError:
            return ToolResult(ticket_id, "timeout")
        except ValueError:
            return ToolResult(ticket_id, "invalid_input")
        # Cancellation and unexpected programming errors propagate.


async def main():
    tools = DemoTools(concurrency=2)
    async with asyncio.TaskGroup() as group:
        tasks = [group.create_task(tools.run(key, delay)) for key, delay in
                 [("T-001", 0.01), ("T-002", 0.4), ("BAD", 0.01)]]
    print(json.dumps({"results": [asdict(t.result()) for t in tasks],
                      "peak_concurrency": tools.peak}, indent=2))


if __name__ == "__main__":
    asyncio.run(main())

import asyncio
import unittest
from async_tools import DemoTools


class AsyncToolsTests(unittest.IsolatedAsyncioTestCase):
    async def test_success_and_validation(self):
        tools = DemoTools()
        self.assertEqual((await tools.run("T-1", 0)).status, "ok")
        self.assertEqual((await tools.run("BAD", 0)).status, "invalid_input")

    async def test_timeout_releases_slot(self):
        tools = DemoTools(1)
        self.assertEqual((await tools.run("T-1", 1, 0.02)).status, "timeout")
        self.assertEqual(tools.active, 0)
        self.assertEqual((await tools.run("T-2", 0)).status, "ok")

    async def test_concurrency_bound(self):
        tools = DemoTools(2)
        result = await asyncio.gather(
            *(tools.run(f"T-{i}", 0.01, 2) for i in range(8)))
        self.assertTrue(all(r.status == "ok" for r in result))
        self.assertLessEqual(tools.peak, 2)
        self.assertEqual(tools.active, 0)

    async def test_cancellation_propagates_and_cleans_up(self):
        tools = DemoTools(1)
        task = asyncio.create_task(tools.run("T-1", 10, 20))
        await asyncio.sleep(0)
        self.assertEqual(tools.active, 1)
        task.cancel()
        with self.assertRaises(asyncio.CancelledError):
            await task
        self.assertEqual(tools.active, 0)
        self.assertEqual((await tools.run("T-2", 0)).status, "ok")

    async def test_queue_wait_uses_deadline(self):
        tools = DemoTools(1)
        async with tools.limit:
            result = await tools.run("T-1", 0, 0.02)
        self.assertEqual(result.status, "timeout")
        self.assertEqual(tools.peak, 0)

权限中最容易误解的地方

allowed_tools（TypeScript 为 allowedTools）是自动许可规则，不能简单理解为“只有这些工具存在”。未列出的工具仍可能受模式及其他规则影响；canUseTool 也不是所有调用必经的鉴权入口。需要全调用检查时阅读 PreToolUse Hook；资源归属和交易规则仍由企业工具服务强制验证。权限评估说明

分别测试允许、拒绝、需要人工输入三条路径，并核对真实工具执行记录。运行目录、工具许可与操作系统沙箱是不同层。会话恢复不撤销外部写入，分叉也不是数据库回滚。会话机制

Python 最小上手

在独立 uv 项目中执行 uv add claude-agent-sdk，按官方指南配置凭据和运行环境。SDK 不自动加载 .env；运行二进制是否随安装包提供，按平台和安装方式确认。安装指南

下面是原创教学片段，用于观察异步消息与最终结果；禁用工具，不进行文件操作。未联网实测，运行前与锁定版本核对字段。

import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions, ResultMessage

async def main():
    options = ClaudeAgentOptions(disallowed_tools=["*"], max_turns=2)
    async for event in query(
        prompt="将学习异步工具调用拆成三个可验收步骤，不执行操作。",
        options=options,
    ):
        if isinstance(event, ResultMessage):
            print(event.subtype)
            print(event.result)

if __name__ == "__main__":
    asyncio.run(main())

query 提供异步消息迭代；最终消息与中间工具消息分开消费。下一步接只读工单工具并检查实际执行，最后加入审批后的提交能力。最终文本和业务数据库提交成功不能混为一谈。

四天学习与验收

  1. 第一天：最小调用与只读工具。交付版本清单、消息时序图和工具执行证据。
  2. 第二天：Hook、权限规则与人工输入。验收拒绝后无副作用，不能跨租户读取。
  3. 第三天：会话恢复、分叉和一个检索 Subagent。验收子任务只获得必要信息，分叉不误用原业务审批。
  4. 第四天：跑统一项目的 60 条练习集，加入重启与回执丢失测试，记录任务质量、预算和失败原因。

生产组合建议：Python 服务负责认证、任务接口和账本，SDK 负责智能阶段，工具服务负责事务与授权。跨小时审批可交给现有持久任务或工作流。不要让 SDK、外层图和队列同时重试同一个写动作。

面试自测

Q1 · Agent SDK 与 Client SDK 有什么区别？

**参考答案：**前者提供循环和工具运行能力，后者更接近模型 API，需要应用自行组织更多执行逻辑。根据复用程度与控制需求选择。**追问：**还需要后端吗？答：认证、业务状态、权限与交付接口仍需设计。

Q2 · allowed_tools 是严格白名单吗？

**参考答案：**不能这样概括，它属于自动许可规则，实际行为与禁用配置、权限模式等有关。应验证完整组合。**追问：**怎样禁止工具？答：使用明确禁用机制，并验证工具定义和执行两层。

Q3 · 为什么不能只在 canUseTool 中鉴权？

**参考答案：**部分调用在更早的规则或模式中获准，不经过该回调。全调用控制参考 PreToolUse，最终业务授权仍在工具服务。**追问：**Hook 能代替数据归属校验吗？答：不能，直接调用服务也必须校验。

Q4 · Session 恢复是否保证外部动作恰好一次？

**参考答案：**不保证。外部提交可能成功而本地回执丢失，需要稳定幂等键、结果查询和操作账本。**追问：**Fork 能撤回原操作吗？答：不能，它是上下文分支。

Q5 · 怎样使用 Subagent 才有收益？

**参考答案：**拆分独立、可验收的任务，限制工具、上下文和预算，先与单 Agent 基线比较。**追问：**子 Agent 输出能直接提交吗？答：父流程仍需验证证据与业务规则。

Q6 · 如何与 LangGraph 组合？

**参考答案：**将 SDK 封装为输入、结果和错误边界清晰的节点或服务。图管理外部流程，SDK 管理内部循环，明确审批与重试归属。**追问：**图重试就创建新会话？答：不能默认这样做，要先确定恢复与副作用语义。

Q7 · 生产验收要看什么？

**参考答案：**权限、隔离、取消、预算、进程生命周期、恢复范围和外部动作一致性；轨迹必须关联真实业务结果。**追问：**内置工具完善就不需故障测试？答：实际部署和企业集成仍会产生新的故障边界。

22 DeepSeek Harness：插件化运行支撑层

官方项目与成熟度

本章核验日期：2026-09-16。这里指 DeepSeek 官方 deepseek-ai/deepseek-harness（命令名 dsh），不是任何 DeepSeek 模型工具循环的泛称，也不是 LangChain 生态的 Deep Agents。官方当前标注 Developer Preview（开发者预览版），明确可能出现破坏兼容的变更。以固定版本或提交进行学习和 PoC（Proof of Concept，概念验证）。官方仓库

Harness（运行支撑层）组织模型之外使任务持续执行的能力。DeepSeek Harness 基于 Cordis，将工具、模型适配、会话、存储、沙箱、循环等作为可组合能力。它与模型 API 的区别在于执行环境，与显式业务图的区别在于组合和生命周期抽象。官方介绍

核心概念

Concept（概念） 学习重点 验收问题
Cordis（插件组合内核） 插件服务、事件与生命周期 卸载是否释放注册与资源？
Plugin（插件） 提供可组合能力 契约、依赖和权限是否明确？
Profile（运行配置组合） 指定启动组合和配置 实际启动了哪些组件？
Bundle（能力分发包） 分发代码与配置 覆盖顺序和依赖是否可复现？
Session Event（会话事件） 需保留的交互事实 恢复后保留什么？
Agent Event（运行事件） 执行中的观察与控制 不能假定每种事件都持久化
Trajectory（执行轨迹） 检查上下文、工具与结果 能否定位最早的错误步骤？
PTC（Programmatic Tool Calling，程序化工具调用） 用程序组织多步工具操作 是否减少往返，是否增加执行风险？

架构文档区分 Profile、Bundle 和事件域，并描述 Python 客户端通过运行时启动 SDK Profile 的路径。因此不是“只能在浏览器运行”，也不能理解为纯 Python 原生编排库。预览版的模块与启动方式应按选定提交确认。Architecture

运行模式怎么学习

官方展示 Standard（标准）、PTC（程序化工具调用）、Minimal（极简）和 Creative（创造）等模式，分别用于常规工具组合、代码组织操作、极小工具环境和自定义组合探索。模式是对照实验入口，不是性能排名。PTC 仍需逐工具授权与资源预算；工具少也不代表必然更安全。模式介绍

企业集成与回放边界

下面是教学架构示意，不是 SDK 配置语法：

企业任务 API → 可信身份与工作区绑定
            → 固定版本的 Harness Profile
            → 模型 / 工具 / 权限 / 存储插件
            → 企业工具服务（授权、幂等、审计）
            → 结果与轨迹关联

优先通过支持的组合和扩展机制定制，稳定业务工具协议和回归集。插件可卸载，不代表插件已执行的外部写入会自动撤销；插件化也不自动形成不可信插件间的强隔离。工作区、Shell、网络和资源限制应在所选后端验收。

追加式会话日志有助恢复与检查，但 Replay（回放）不应默认重新执行写工具。需要区分持久事实与运行事件，制定脱敏、保留和兼容策略。实际能见到哪些模型推理内容取决于模型和事件，不承诺始终获取完整内部推理。

面试自测

Q1 · Model 和 Harness 各解决什么？

**参考答案：**Model 提供生成与推理，Harness 组织上下文、工具、状态、循环和环境交互。相同模型配不同执行设计可能得到不同结果，需控制变量验证。**追问：**更强模型能解决所有失败吗？答：不能修复权限和事务设计错误。

Q2 · 一切皆插件有什么价值？

**参考答案：**使组合和生命周期显式化，便于替换能力，减少直接修改核心；代价是依赖、配置与版本治理。**追问：**插件越多越好吗？答：只引入需求证明必要的能力。

Q3 · Profile 和 Prompt 有何区别？

**参考答案：**Profile 组织实际组件和运行配置，Prompt 只是模型输入的一部分。Prompt 不能替代工具服务或沙箱。**追问：**同 Prompt 为何行为不同？答：工具集合、上下文和运行策略可能不同。

Q4 · PTC 的收益和风险是什么？

**参考答案：**用代码组合条件、循环和操作可减少部分模型往返，但收益依任务而定；需控制资源、权限和错误传播。**追问：**批量执行能跳过授权吗？答：每个实际动作仍需服务端校验。

Q5 · Append-only 日志能保证恢复正确吗？

**参考答案：**它保存事实序列，但还需持久化保证、格式兼容、恢复语义与副作用处理。日志存在不等于恰好一次。**追问：**回放写工具怎么办？答：默认回放记录，不重复写入；重执行必须另有受控语义。

Q6 · 插件卸载会回滚外部业务吗？

**参考答案：**通常只释放注册与运行资源，不撤销已创建工单或订单，业务需要补偿。**追问：**如何测试？答：检查监听器、连接、后台任务与在途请求收尾。

Q7 · Developer Preview 应如何使用？

**参考答案：**固定版本、隔离试点，验证回归、升级与回退，不把主分支能力当稳定承诺。**追问：**是否完全不能生产用？答：根据明确范围和验收证据判断，不能仅凭预览标签或演示下结论。

Q8 · 如何证明 Harness 优化有效？

**参考答案：**固定模型、数据集、预算和评分，仅改变一个运行因素，比较成功率、工具正确率、长尾延迟及每成功任务成本。**追问：**演示成功一次够吗？答：需覆盖失败、恢复、权限及重复运行。
